# Connector 期望架构

状态：设计草案，不代表当前运行时能力
核验日期：2026-08-26
范围：只定义平台接入、能力目录、适配器声明、连接实例、能力路由和动态解析；不实现注册中心、凭据、网络调用或平台 adapter。

## 1. 结论

Connector 不能只是 `platform + credential + capabilities[]`，也不能拥有“抖音是什么”的平台知识。平台概念、能力语义和接入方法属于版本化 `PlatformKnowledgeSnapshot`；Connector 只负责把其中一个接入方法绑定到本机 adapter、账号和凭据引用，并获取信息。

完整知识/事实/投影边界见 [平台知识、事实仓库与动态投影架构](./PLATFORM_KNOWLEDGE_ARCHITECTURE.md)。系统运行时真正需要解析的是：

长期情况下，knowledge snapshot、Platform Skill、固定开源 artifact、adapter ref 和 verification report 共同组成版本化 [Platform Pack](./PLATFORM_DISCOVERY_LONG_TERM_ARCHITECTURE.md)；Connector 只消费其中已验证的执行声明。

Platform Pack 还保存 `CapabilityAdoptionDecision`。它显式区分 eligible、manual-only、partner-only、deferred 和 rejected；否则“没有 route”无法区分尚未研究与经证据审查后拒绝。Connector resolver 只能消费 eligible/manual/partner 且满足条件的声明，不能因为发现社区 MCP 或 private API 就自行改写 adoption。

Channel Pack 位于 Connector 之上，只组合多个固定 Platform Pack、roster/query scope 和 projection policy。它不生成跨平台 Connector，也不把多个成员授权合并成一个 route；Collection Planner 必须分别 resolution/bind 每个成员 capability，再在事实层组合结果。

> 在指定 scope、目的和政策下，针对某个平台/账号，当前是否存在一条经过证据验证、已授权、健康且预算允许的能力路由；如果存在，应通过哪个最小端口执行。

期望模型分成六层：

```text
PlatformKnowledgeSnapshot  平台概念、能力和接入方法的版本化知识
CapabilityDefinition       系统要完成的稳定语义操作是什么
AdapterDefinition          某段代码实现哪个接入方法及如何映射
ConnectorInstance          本机配置了哪个账号、配置和凭据引用
CapabilityResolution       此刻、此目的下哪条 route 实际可用
Observation                Connector 实际获取的追加式具体事实；可附 representation、原生 revision/history、aggregate provenance 与远程文档 manifest
```

其中 `CapabilityRoute` 是知识 snapshot、Adapter 声明与 Connector 配置绑定后的候选路径，`ConnectionProfile` 是用户显式组合多条 Connector 的逻辑平台连接。每次 resolution 和 observation 固定 snapshot ID，避免平台知识升级后无法解释历史运行。Adapter 只能把 provider 明示的版本/关系写为 native metadata；根据重复采集得到的 hash 变化必须标成 observed snapshot。官方标准映射、HTML presentation 和 manual extract 必须写 `SourceRepresentationMetadata`，不能冒充 provider-native。附件 URL 先产出 descriptor，不能在 Read 端口中假装已获取或已获再利用权。

## 2. 设计目标

- 新增平台主要增加 concept/capability/access-method knowledge、adapter route 和 connector 配置，不修改核心对象结构。
- 同一平台可以同时存在官方 API、sidecar、浏览器辅助、导出文件和人工交接路线。
- 同一账号可以用不同 adapter 完成读取、发布、分析和对账。
- 能力是否可用按 route 动态解析，不给整个平台一个永久的绿色勾。
- 读取与外部副作用具有不同确认、幂等、对账和失败语义。
- 平台私有 payload 不进入核心类型，只通过版本化 mapping/extension 传递。
- 每次解析和调用都能关联政策、健康、证据、限流、成本、run 和 attempt。

非目标：

- 不用一个 `Invoke(any) any` 取代类型化端口。
- 不把浏览器可操作误报成官方 API。
- 不在 Connector 对象中保存 Cookie、token 或其他明文 secret。
- 不从用户名、头像或手机号自动推断跨 adapter、跨平台账号归属。
- 不让 fallback 绕过批准、政策或 unknown reconciliation。

## 4. PlatformKnowledgeSnapshot：概念、能力与接入方法

`PlatformDefinition` 只描述平台身份。`PlatformConceptDefinition` 描述 video、creator、comment、metric 等类型和关系；`PlatformCapabilityDefinition` 描述 search/read/publish 等能力如何作用于这些概念；`AccessMethodDefinition` 描述有证据的官方 API、公开 feed、授权导出、浏览器或人工接入表面。四者作为一个 `PlatformKnowledgeSnapshot` 版本化提交。

它们不保存具体账号、视频、评论、credential、connector health 或运行时状态；具体数据由 Connector 获取后写入分析事实仓库。

一个平台能力定义表达：

- capability ID/version、subject/result concepts 与可证明的 access method；
- 适用账号类型、region 和 required scopes；
- 官方文档、SDK、条款或 live probe 证据；
- checkedAt、expiresAt 和 confidence。

平台知识不代表当前环境可调用。比如平台官方开放 analytics，只说明理论入口存在；没有 adapter、账号授权或健康 connector 时，resolution 仍是 blocked。

平台 ID 不进入 capability ID。`github`、`douyin`、`xianyu` 是平台；`discovery.search.videos`、`analytics.read.content-metrics`、`account.publish.video.private` 是可由不同平台映射的细粒度语义。

## 5. CapabilityDefinition：稳定能力语义

CapabilityDefinition 是系统与业务流程依赖的稳定契约，至少定义：

| 维度 | 示例 | 作用 |
| --- | --- | --- |
| domain | session、discovery、content、engagement、analytics、media、live、account | 领域归类 |
| surface | platform、local、manual | 能力由平台、本地处理还是人工交付 |
| action | search、read、receive、execute、reconcile | 操作语义 |
| resource | content-item、comment、listing、job | 处理对象 |
| access | public、owned、authorized、partner | 数据授权范围 |
| effect | none、local-write、platform-write | 与当前运行切片一致的副作用边界 |
| reversibility | reversible、irreversible、unknown | 外部结果能否可靠撤销 |
| delivery | pull、push、manual | 数据/动作交付方式 |
| idempotency | unsupported、system-key、provider-key | 重试边界 |
| reconciliation | read-after-write、provider-job、manual-evidence | unknown 处理 |
| confirmation | none、policy-dependent、one-time-human | 批准要求 |
| input/output schema | versioned schema ref | 稳定交换契约 |

Capability ID 使用 `<domain>.<action>.<resource>[.<qualifier>]`，约束如下：

- 不编码平台名、adapter 名、账号名和接入模式，但必须细到调用者能理解真实结果和副作用。
- 小版本差异通过 adapter mapping 吸收。
- 输入、输出或副作用语义不兼容时发布新 capability version。
- 新能力通过 Catalog 注册，不在 Connector 上增加固定布尔字段。

当前抖音运行切片的细粒度目录可以直接成为首个 compatibility profile，例如：

```text
session.inspect
discovery.search.videos
content.read.video
engagement.read.comments
engagement.read.comment-replies
analytics.read.content-metrics
media.download.video
media.transcribe.video
account.publish.video.private
```

`job.search.public`、`listing.create.owned`、`message.send.owned` 等只有出现明确业务用例、政策和契约后再注册，避免先造一个无法验证的大全。本地转写这类 `surface=local` 能力不要求平台官方 claim；平台读取和写入则必须有平台证据。

## 6. AdapterDefinition：代码声明与映射

AdapterDefinition 描述一个有版本的软件或人工 adapter，包括：

- supported platforms（可为空，表示平台无关）、kind、runtime、license、config schema 和 secret field 名称；
- 一组 `AdapterCapabilityRoute`；
- 每条 route 的 access method、capability、最小 ports、账号类型和 scopes，以及它完成 conformance 时依据的 knowledge snapshot；
- 平台输入/输出到核心 Schema 的 mapping；
- `direct/coupled/outbox-only/not-implemented`、coupled capabilities；
- idempotency、reconciliation、confirmation 等语义；
- cost、latency、coverage、reliability 等有序质量等级；
- 默认 limits、maturity、证据和 conformance suite。

Adapter 声明的是理论能力，不保存当前账号状态。能力成熟度必须按 route 记录，例如同一 adapter 可以：

```text
content.read.video             verified
analytics.read.content-metrics experimental
account.publish.video.private  suspended
```

不能只给整个 adapter 一个 maturity。

## 7. ConnectorInstance 与 ConnectionProfile

ConnectorInstance 是一个 adapter 的本机配置实例：

```text
scope + platform
adapter ID/version + config ref
account binding ref + credential bindings
lifecycle + authorization state + granted scopes
enabled route names
```

它不内嵌 `EffectiveCapabilities`，原因是可用性会随政策、健康、限流、证据过期、预算和调用目的变化。

Connector 生命周期与其他状态分开：

| 轴 | 状态 |
| --- | --- |
| 配置生命周期 | registered、configured、disabled、retired |
| 授权 | not-required、missing、pending、valid、expired、revoked |
| 健康 | ready、degraded、blocked、unknown |
| 成熟度 | experimental、community、verified、production、suspended |
| 政策 | allowed、denied、allowed-with-obligations |

这些轴不能压成一个 `callable: true/false`。

ConnectionProfile 是用户显式创建的逻辑连接，用于组合一个平台/账号的多条 Connector。例如：

```text
connection: douyin-owned-account-A
  connector-1: research sidecar        discovery.search.videos/engagement.read.comments
  connector-2: creator browser adapter account.publish.video.private
  connector-3: official analytics API  analytics.read.content-metrics
  connector-4: manual evidence         account.publish.video.private reconcile port
```

Profile 只组合用户确认属于同一账号或业务上下文的 connector，不自动做身份推断。

## 8. CapabilityRoute 与动态解析

CapabilityRoute 是 adapter route 与 connector instance 的绑定结果，包含：

- knowledge snapshot、access method、platform、connector、adapter/version 和 declaration name；
- capability ref、mode 和 ports；
- input/output mapping 与执行语义；
- limits、maturity、priority 和 enabled 状态。

业务层发出 CapabilityRequirement，而不是直接指定 adapter：

```text
capability       = discovery.search.videos/v1
platform         = douyin（可选）
acceptedAccess   = public
acceptedModes    = official-api, manual-import
minimumMaturity  = verified
allowedEffects   = none, local-write
requireReconcile = false
allowManual      = true
allowCoupled     = false
strategy         = highest-reliability
budget           = 本次条数/速率/费用上限
```

Resolver 按顺序评估：

1. capability definition 是否存在且版本兼容；
2. knowledge snapshot 中的平台能力与 access method 是否有未过期证据；
3. adapter 是否声明兼容 route，mapping/conformance 是否通过；
4. connector 是否 enabled/configured；
5. 账号类型、authorization 和 granted scopes 是否满足；
6. policy 是否允许当前 principal/purpose/effect；
7. route health、rate limit、成本和 kill switch 是否允许；
8. requirement 的 mode、maturity、reconcile 和 budget 是否满足；
9. 对候选 route 排序，生成带 expiresAt 的 CapabilityResolution。

Resolution 保留所有候选及不满足条件的原因，不能只返回选中的 adapter。Workbench 因而可以解释“为什么降级到人工导入”或“为什么拒绝自动发布”。

## 9. 端口与调度边界

Resolver 选择 route，但不提供万能动态调用。执行面仍使用类型化小端口：

| 能力形态 | 端口 |
| --- | --- |
| 发现流/资源 | StreamDiscoverer |
| 拉取 | PullReader |
| webhook/event | PushReceiver |
| 删除/撤权追踪 | ChangeReconciler |
| 人工导入 | ManualImporter |
| Probe 校验/预览/准备 | ProbeValidator、ProbePreviewer、ProbePreparer |
| 外部执行 | ProbeExecutor |
| unknown 反查 | ProbeReconciler |
| 可选中性取消 | ProbeCanceller；仅当 capability 证明无未审查 serving/analysis effect |
| 产品实验生命周期 | exact capability + ExperimentLifecycleIntent；draft/publish/start/stop-assignment/stop-analysis/serve-treatment/rollback 分离 |
| 指标读取 | MetricCollector |

选中 route 后，Resolver 为具体 port 签发有期 `PortBinding`：

```text
resolution ID + route ID + connector ID
knowledge snapshot + access method
adapter/version + capability/version + port + mode
boundAt + expiresAt
```

类型化端口接收 PortBinding，而不是重新从裸 ConnectorInstance 猜 route。同步代码仍用 request context 传播 deadline/trace；PortBinding 负责跨队列、批准和人工交接冻结选择结果。Binding 过期必须重新 resolve，不能静默切到另一 provider。

一项 capability 可以绑定多个阶段 port，例如 `account.publish.video.private` 通常要求 validate、preview、prepare、execute，并根据平台语义额外要求 reconcile。不存在的阶段必须在 route declaration 中显式缺失，不能由占位方法在运行时返回 unsupported。

Fallback 重新走 resolution、policy 和 approval：

- 读取型 route 失败，可以按要求切换到另一个已允许 route；
- 外部执行一旦返回 unknown，禁止切换 route 重发，必须先对原 attempt reconcile；
- 从自动路线降级为 manual-package 会生成新的 preview/intent，并重新验证批准范围。
- platform-write 的 preview、approval、intent 和 attempt 都绑定同一 resolution/route；adapter version、capability version、route 或 payload 变化使批准失效。

## 11. 可观测性

可观测对象是 route 和 resolution，而不是只统计平台：

产品实验 route 还必须观测 phase/config revision drift、assignment distribution、exposure lag、SRM/crossover、metric watermark、approval/notification、serving/analysis state divergence、unknown lifecycle writes 与 rollback readiness。一个“stop succeeded”计数不能证明用户已停止被分配，也不能证明线上 serving 未被改成 winner rollout。

## 12. 与当前 Runtime 契约的关系

现有 `PlatformConnector` 是正确的调用者 facade，不应被另一套 Router 替换。目标模型把它当前的内存声明和排序扩展为可治理的 Catalog、Connection 和 Resolution：

| 当前 PlatformConnector | 目标模型 | 处理 |
| --- | --- | --- |
| connector | ConnectionProfile + resolver facade | 保留调用体验，补 scope/account/strategy |
| definition | CapabilityDefinition | 补 version、surface、schema 和完整执行语义 |
| provider | ConnectorInstance + CapabilityRoute | 补 config/credential ref、authorization、ports、evidence |
| plan | CapabilityResolution | 保留有序 candidates，补 policy/health/limits/conditions/expiry |
| snapshot | catalog/resolution projection | 继续只读展示，不成为配置事实源 |
| generic execute | typed port dispatcher | 保留只读 fallback 和 platform-write 拒绝边界 |

现有运行切片保持不变；后续通用化时建立显式映射：

| 当前对象 | 目标对象 | 说明 |
| --- | --- | --- |
| platform-connector/v1 | Capability catalog + route quality + resolution projection | 保留当前调用者 facade 和五种 routing strategy |
| adapter-manifest | AdapterDefinition + AdapterCapabilityRoute | 固定 capabilities 数组升级为带版本和语义的 route |
| connector-capability | ConnectorInstance + CapabilityResolution | 配置事实与动态可用性拆开 |
| capability-snapshot | HealthSnapshot + resolution projection | 产品完成度、健康和可调用性不再混合 |
| runtime provider | ConnectorInstance + CapabilityRoute | provider 是已绑定 route，不是新的领域层 |
| runtime adapter methods | typed port bindings | submit/verify 等映射到 prepare/execute/reconcile |

当前 snapshot 中未单独携带 capability version 的 ID，在 compatibility profile 中统一映射为该 profile 声明的版本（首版可为 `v1`）；不回写或重新解释已经保存的 `platform-connector/v1` snapshot。

目标 Schema 成为 normative 之前，`design/go/demandintel` 仍只是候选设计视图，不能替代现有 Host/CLI/Client 事实源。

## 13. 架构验收

进入 Connector Runtime 实现前，至少用 fixture/contract scenario 证明：

- 新平台能只通过 catalog + adapter route 加入，无需修改 Connector 核心字段；
- 同一平台的 read、probe、analytics 可来自不同 adapter；
- webhook、polling、manual import 都产出统一 Observation；
- 缺凭据、scope 不足、证据过期、health degraded、rate limit 和 policy deny 有不同 condition；
- resolver 能解释候选路线未被选择的原因；
- manual fallback 不冒充自动能力；
- execute unknown 不会触发跨 route 重发；
- connection grouping 只来自用户声明，不进行身份推断；
- capability、adapter、connector、route 和 resolution 均有独立版本/生命周期；
- 所有异步调用保持 correlation/run/attempt，并有 route 级健康和 SLO。
