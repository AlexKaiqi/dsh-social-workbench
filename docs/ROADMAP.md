# 路线图

这不是交付日期承诺，而是降低未知性的顺序。每一阶段只有在证据和验收满足后才进入下一阶段。

## R0：运行准备（当前）

范围已经固定为抖音和小红书。准备一组用户有权使用的来源与媒体、两个可登录账号和手机；明确发布前逐条确认，确定 receipt 用 URL、截图还是平台回调。

退出条件：可以用 3–10 条用户提供的 URL、截图、文字或附件开始一次真实任务。此阶段不要求全站采集 API，也不冻结完整领域 schema。

## R1：Run 0，人工手机交接

复用 DSH WorkSurface/附件保存输入和草稿，复用 Pocket 在手机打开同一工作台。生成一份 brief、抖音版、小红书版和各自发布包；用户在官方 App 完成最终确认并回填结果。

退出条件：两个平台各完成一次真实发布或草稿保存；取消和失败没有被记成成功；同一流程第二次运行无需改代码。

## R2：Run 1，官方移动 Share SDK

取得抖音和小红书 App Key 后，构建一个薄 Android companion，只负责下载一次性任务、调起各自官方 SDK、回传 session/错误/取消状态。

退出条件：两个平台均能从同一手机入口进入官方编辑器并返回可核验的流程结果。只抽取两边真实重复的 handoff 状态机。

## R3：Run 2，抖音服务器 OpenAPI

只有 `video.create` 等权限实际获批后才实现 OAuth、token、上传、创建、审核状态和授权账号作品读取。小红书继续用官方 Share SDK，不假设存在服务器静默发布能力。

退出条件：抖音测试账号完成一次创建并读回审核/作品状态，撤权、错误和不确定结果可见。

## R4：基于证据的信息处理

先完善用户导入、证据回链、需求 brief 和两个平台的内容差异。只有真实任务证明需要更多来源时，才增加授权账号 API 或其他合法公开来源。

退出条件：结论能回到输入材料；同一输入可复算；模型生成事实与来源事实可区分。

## R5：按运行结果重构和扩平台

重复的 receipt、媒体校验、重试或 handoff 状态实际出现后再组件化。第三个平台只有在操作语义和目标价值明确时接入，不为平台数量使用 Cookie、私有签名或验证码绕过。

## 当前 MVP

```text
3–10 条用户提供的素材
  -> 1 个 brief
  -> 抖音版 + 小红书版
  -> 手机端用户确认
  -> 两个平台的真实 receipt
  -> 用同一流程再跑一次
```

详细步骤和准入条件见[抖音 + 小红书最小可运行闭环](MVP_DOUYIN_XIAOHONGSHU.md)。衡量标准是能否真实重复，不是 schema 数量、框架数量或平台数量。
